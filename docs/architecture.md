# Архитектура

## Принцип
Ранжирование и фильтрация — детерминированный код. LLM используется только
для формулировки текста объяснения поверх уже посчитанных фактов. Это разом
даёт: детерминизм порядка карточек, объяснения без общих фраз и устойчивость
к сетевым сбоям (<10с ответ даже если LLM API недоступен).

## Пайплайн

```
Клиент (форма) ──POST /recommend──▶ API (FastAPI)
                                          │
                                          ▼
                              1. Query Normalizer      Pydantic: валидация, нормализация
                                          ▼
                              2. Candidate Pool         все профили city + category (real + synthetic)
                                          ▼
                              3. Hard Filters           busy_dates, budget, format, duration, language
                                 (чистые функции)
                                          ▼
                              4. Outcome Classifier  ──▶ NO_CATEGORY / NO_MATCH / FOUND
                                          │ (FOUND)
                                          ▼
                              5. Deterministic          semantic score (эмбеддинги) + soft-фичи
                                 Scorer & Top-3          сортировка + tie-break по id
                                          ▼
                              6. Explanation Agent      LLM temp=0, grounded фактами,
                                 (tool-grounded)         кэш + fallback на шаблон
                                          ▼
                              7. Response Assembler     карточки + outcome + trace для жюри
```

## Hard Filters
Все — чистые булевы функции над одним профилем (`src/neuroforge/filters.py`).
Фильтры разделены на два уровня, и разделение несёт смысл для исхода:

**POOL-фильтры** — определяют, существует ли такой каталог вообще:

| Фильтр | Условие |
|---|---|
| city | `profile.city == query.city` |
| category | `query.category in profile.categories` |

**CANDIDATE-фильтры** — отсеивают внутри существующего каталога. Заданы
реестром `CANDIDATE_FILTERS`, порядок значим (см. ниже):

| Фильтр | Условие |
|---|---|
| busy_dates | `query.date not in profile.busy_dates` |
| budget | `profile.price_from_kzt <= query.budget_kzt` |
| event_format | `query.event_type in profile.event_formats` |
| duration (опц.) | `profile.max_hours is None or profile.max_hours >= query.duration_h` |
| language (опц.) | `query.language in profile.languages` |

Порядок реестра задаёт две вещи: воронку в трассировке и то, какая причина
считается **основной**, если кандидат не проходит сразу по нескольким. Порядок
соответствует формулировке ТЗ («заняты на дату, не тянут бюджет, не берут этот
формат»). Каждый отсеянный учитывается ровно один раз — числа в объяснении
сходятся с `pool_size - found_count` (покрыто тестом).

Добавление нового фильтра = одна строка в реестре: `outcome.py`, `pipeline.py`
и схема трассировки не меняются.

## Outcome Classifier
```
pool = POOL-фильтры(city, category)
if pool пуст:            → NO_CATEGORY   # «в этом городе такой категории нет»
survivors = воронка CANDIDATE-фильтров(pool)
if survivors пуст:       → NO_MATCH      # + breakdown причин, числами
else:                    → FOUND         # found_count < 3 → message с причиной
```
Различие NO_CATEGORY и NO_MATCH принципиально: первое — «мы такого не возим»,
второе — «возим, но конкретно на ваших условиях никто не проходит». Пользователю
это разные ответы, и ТЗ требует их различать явно.

## Deterministic Scorer

### Почему у запроса есть свободный бриф
Структурные поля запроса (город, категория, формат, язык, длительность) у всех
выживших кандидатов совпадают **по определению** — они прошли одни и те же
жёсткие фильтры. Значит, текст, собранный из этих полей, одинаков для всех
кандидатов, и семантическое сходство с ним мерило бы не релевантность, а
случайное совпадение слов описания с названием категории.

Поэтому `Query` содержит опциональное поле `brief` — свободное описание
пожеланий («нужен ведущий на двух языках с опытом больших корпоративов»).
Это единственный вход, с которым сравнение описаний осмысленно, и он же даёт
опору критерию ТЗ «совпадение **по смыслу описания**».

Если брифа нет — семантическая фича отключается, а её вес перераспределяется
между остальными. Сервис не ломается, просто ранжирует по структурным фактам.

### Формула
```
score = w.semantic_similarity * similarity(query.brief, profile.description)
      + w.budget_headroom     * budget_headroom(profile.price_from_kzt, query.budget_kzt)
      + w.duration_margin     * duration_margin(profile.max_hours, query.duration_h)
      + w.language_breadth    * language_breadth(profile.languages, query.language)
```
Веса — в `config.Settings.scoring`, не в коде. Эмбеддинги считаются локально
(`sentence-transformers`, мультиязычная модель) — без сетевой зависимости на
критичном пути. Сортировка `desc(score)`, tie-break по `id` asc.

### Осознанное решение про цену
`price_from_kzt` — цена «от», нижняя граница. Дешевле **не** значит лучше,
поэтому `budget_headroom` получает малый вес: запас по бюджету — это факт для
объяснения («укладывается с запасом 23%»), а не преимущество в ранжировании.
Иначе ведущий за 100 тыс. систематически обгонял бы ведущего за 900 тыс. при
бюджете в миллион, что не соответствует реальности рынка.

## Explanation Agent
Для каждого top-k кандидата собирается структурированный факт-объект и
передаётся в LLM с инструкцией использовать **только** эти факты, 1-2
предложения, без общих фраз. temperature=0. Кэш по
`hash(candidate_id + normalized_query)`. При таймауте/ошибке — шаблонный
fallback на тех же фактах.

Состав фактов:

| Факт | Зачем |
|---|---|
| `budget_headroom_pct` | «укладывается в бюджет с запасом 23%» |
| `duration_margin_h` | «берёт до 8 часов при ваших 5» |
| `language_match` | «работает на казахском и русском» |
| `top_semantic_sentence` | предложение из описания, ближайшее к брифу |
| `free_while_n_busy` | «свободен на 14 ноября, тогда как 7 из 15 в категории заняты» |
| `is_synthetic` | в демо видно, где реальный профиль, а где добавленный |

`free_while_n_busy` добавлен намеренно: DoD требует, чтобы при смене даты было
видно **в объяснении**, что дело в занятости, а не только в изменившемся
составе карточек.

Факты у кандидатов различаются по построению (разные цены, часы, языки, разные
предложения из описаний) — это и обеспечивает требование DoD «если стереть
имена, карточки одного запроса нельзя перепутать между собой».

## Гибкость / принцип "ничего не хардкодить"
- Допустимые города/категории/форматы/языки вычисляются из датасета
  динамически (`data_loader.py`), не перечисляются в коде.
- Веса скоринга — конфиг, не константы в коде.
- Набор жёстких фильтров — реестр `CANDIDATE_FILTERS`; добавление фильтра не
  трогает классификатор исходов, пайплайн и схему трассировки.
- Набор soft-фич скоринга — список функций, легко расширяемый.
- Счётчики в `PipelineTrace` — словари, а не фиксированные поля, иначе новый
  фильтр ломал бы схему ответа.
- Промпт LLM — отдельный шаблон, не встроенная строка в логике.

Жёстко задана только **схема** данных (имена полей датасета), не их содержимое.

## Данные
`hackathon-dataset-anonymized` — 66 профилей: id, anon_name, categories, city,
price_from_kzt, event_formats, languages, max_hours, busy_dates, description,
synthetic, city_imputed, price_imputed. 13 профилей полностью синтетические.
Можно дописывать свои синтетические профили в `data/synthetic/` тем же
форматом — в демо видно, где реальный профиль, а где добавленный
(`Card.is_synthetic`).

## Демо-сценарии (обязательны)
1. Плотная категория, осенняя дата (Ведущий — 15 / Фотограф — 12 / Банкетный зал — 8).
2. Редкая категория (Флорист/Декоратор/Сувениры/Ведущий церемонии/Фотобудки/Отель/Инструменталист — по 3).
3. Запрос без результата — с текстовым объяснением.

Пустые исходы берутся из реальных дыр в данных, а не подстраиваются:
* **NO_CATEGORY** — все 3 «Декоратора» находятся в Алматы, в Астане их нет.
  Второй такой случай: город «Зарубежье» представлен единственным профилем
  (фотограф), любая другая категория там пуста.
* **NO_MATCH** — декабрьские выходные в плотных категориях: по условию задачи
  загрузка декабря 70–80%, и вместе с ограничением бюджета каталог выносится
  полностью. Это сезон, а не дефект датасета.

## Особенности датасета, влияющие на логику
* Окно `busy_dates` — ровно 100 дней, 23.09.2026–31.12.2026. Запрос на дату вне
  окна означает «данных о занятости нет», и все считаются свободными.
* Профилей без занятых дат нет ни одного — «всегда свободных» не существует.
* 13 профилей мультикатегорийны (напр. Ресторан + Банкетный зал). В карточке
  показывается **запрошенная** категория, а не первая из списка профиля.
* 13 профилей помечены `synthetic: true` уже в исходных данных — это поставка
  организаторов, не наши добавления. Наши (если появятся) лежат отдельно, в
  `data/synthetic/`, и загрузчик требует от них `synthetic: true`.
* Цены: от 100 тыс. до 6 млн ₸, медиана 600 тыс. Разброс в 60 раз — поэтому
  бюджет работает как жёсткий фильтр, а не как мягкий сигнал.
